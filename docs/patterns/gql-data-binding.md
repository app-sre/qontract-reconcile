# GraphQL Data Binding with `qenerate`

A core pattern in `qontract-reconcile` is the use of `qenerate`, a tool that automatically generates Pydantic data classes from GraphQL queries. This provides a robust, type-safe way to fetch the desired state for an integration from `app-interface`.

This approach avoids manual dictionary parsing and provides benefits like static type checking with `mypy` and editor autocompletion.

## The `qenerate` Workflow

The process involves three main steps:

**1. Define a GraphQL Query (`.gql` file)**

First, you create a `.gql` file in the `reconcile/gql_definitions/` directory (usually within a subdirectory for your integration). This file defines the data your integration needs.

*Example: `reconcile/gql_definitions/glitchtip/glitchtip_instance.gql` (simplified)*
```graphql
# qenerate: plugin=pydantic_v2

query GlitchtipInstance {
  instances: glitchtip_instances_v1 {
    name
    automationToken {
      ...VaultSecret
    }
  }
}

fragment VaultSecret on VaultSecret_v1 {
  url
  path
  field
  version
  format
}
```
**Note:** Use `# qenerate: plugin=pydantic_v2` to generate Pydantic v2 models.

**2. Generate Python Code**

Ensure you run a local GraphQL server on `localhost:4000` with up-to-date schemas.

Next, you run the `make qenerate` command from the root of the repository. This command performs two actions:
- `make gql-introspection`: Fetches the latest GraphQL schema from the server.
- `make gql-query-classes`: Reads your `.gql` file and the schema, and generates a corresponding Python module.

This will create a `glitchtip_instance.py` file next to your `.gql` file, containing Pydantic models that match the query structure.

*Generated file: `reconcile/gql_definitions/glitchtip/glitchtip_instance.py` (simplified)*
```python
# Generated by qenerate plugin=pydantic_v2. DO NOT MODIFY MANUALLY!

from pydantic import BaseModel, ConfigDict, Field

from reconcile.gql_definitions.fragments.vault_secret import VaultSecret


class ConfiguredBaseModel(BaseModel):
    model_config = ConfigDict(extra="forbid")


class GlitchtipInstanceV1(ConfiguredBaseModel):
    name: str = Field(..., alias="name")
    automation_token: VaultSecret = Field(..., alias="automationToken")


class GlitchtipInstanceQueryData(ConfiguredBaseModel):
    instances: list[GlitchtipInstanceV1] = Field(..., alias="instances")
```

The generated module also provides `query(query_func=...)`, which executes the
query through the supplied callable and validates the response into these models.
Never edit generated files manually; change the query and regenerate instead.

**3. Use the Generated Code in an Integration**

Finally, you can import and use the generated `query()` function in your integration. This gives you fully typed objects to work with.

*Example: `reconcile/glitchtip_api/integration.py` (simplified)*
```python
import logging

from reconcile.gql_definitions.glitchtip.glitchtip_instance import (
    query as glitchtip_instance_query,
)
from reconcile.utils import gql

instances = glitchtip_instance_query(query_func=gql.get_api().query).instances
for instance in instances:
    logging.info(f"Processing Glitchtip instance: {instance.name}")
```

Each instance is a typed `GlitchtipInstanceV1`; nested fields such as
`instance.automation_token` are typed `VaultSecret` models, not dictionaries.

This workflow is the standard and recommended way to fetch data for new integrations.

Glitchtip is an established shared query/model family: its integrations and
tooling reuse `reconcile/gql_definitions/glitchtip/`. Extend the shared project
query for membership sources instead of creating a duplicate API query. Keep
other shared-query consumers compatible and grant schema read permissions for
any newly selected references, even when those consumers do not resolve members.

## Role Membership Sources

Membership sources must be transparent to integration business logic. GraphQL
fetch helpers query `memberSources { ...RoleMembershipSource }` and use
`resolve_role_members` to supply roles with fully resolved users. Downstream
logic processes `role.users` uniformly, whether users came from explicit
configuration, LDAP, or another provider. Provider selection, connectivity,
membership I/O, and source-error handling belong to the shared membership layer,
not downstream compilers or reconciliation logic.

The existing source-independent query and execution scope defines the supplied
role collection; this does not require querying every role in app-interface.
Resolve and validate every role in that collection before normal business
filtering and desired-state construction. Preserve ordinary role, permission,
namespace, and cluster exclusions in source-independent business logic. Do not
add or move those exclusions before resolution merely to avoid provider I/O or
errors: a role being ignored later does not make its sources optional.

Query roles rather than users when LDAP-only roles must be visible, as in
`acs-rbac`. Include `org_username` even for GitHub consumers: it is the resolver's
deduplication key.

Use `resolve_role_members` from `reconcile.utils.membershipsources.resolver`
for synchronous consumers, or the async function of the same name from
`reconcile.utils.membershipsources.async_resolver` for API integrations.
These are the public entry points; there is no separate typed-query wrapper.
They load LDAP settings only when the supplied roles need LDAP, and accept injected
LDAP settings and Vault URLs. Synchronous LDAP resolution uses one event loop
and closes its loop-bound HTTP connections; API integrations reuse their existing
event loop and runner-managed client. Provider resolvers remain dependency-injected.
Forward the supplied `query_func` to the resolver. For `change_owners`, authorization
must use the comparison bundle; current-bundle configuration validation must not
resolve authorization users.

Pass GQL roles directly: resolvers accept the structural `RoleMembershipFields`
Protocol and return a list of roles, not a membership dictionary. By default each
result has the original GQL role type, with resolved users and unchanged metadata.
The input role objects are not mutated. Callers do not assign resolved users back
onto `role.users`; fetch helpers return the adapted roles or containers holding them.
`RoleWithMemberships` documents the optional native `bots` collection, but providers
resolve users only. Native bots remain unchanged and integrations handle them
explicitly alongside users; bots never enter `role.users`.
Prefer each query's generated user model as `user_cls`.
The resolver projects provider attributes onto the target model, supplies `None`
for absent required nullable fields, and validates normally. It does not fabricate
required values or construct unvalidated partial users. Users rejected by
`model_validate` are skipped silently, without reserving their deduplication key.
Valid explicit user attributes take precedence over source-resolved values.

LDAP group members include `name` from the person's `cn` attribute, making the
shared Glitchtip user model compatible. GitHub org/team and owner consumers
silently exclude members without GitHub identities before conversion. Missing
GitHub profiles are expected and must not generate warning-level Slack noise.
GitHub-only bots remain on their existing membership path because they may
lack `org_username`.

OpenShift/OCM generated users require a GitHub string, but LDAP members without
GitHub accounts can still have valid OIDC access. These consumers define their own
typed user and role models and supply `role_cls` explicitly. Slack's permission
and cluster-access consumers similarly own their identity/role models. Shared
membership code contains Protocols, not concrete role/user classes or wrappers. Both modes return
the adapted role directly, without `.role` indirection, optional membership maps,
or downstream "not resolved" guards. Provider failures still abort reconciliation;
skipping invalid individual users can remove their membership and must be reviewed
in the dry-run diff.

Missing groups and resolution errors must fail the complete integration execution
before mutations, not become empty membership or a partial desired state. This
also applies when a supplied role has explicit users or normal business logic
would later ignore it. For example, a missing LDAP group on an ordinary GitHub
member role must still fail an owner run if that role is in the supplied
collection, even though owner compilation ignores its member permission.
A confirmed-empty group is valid; a missing or unresolved group is not.

Keep early exit enabled for source-backed roles: comparison-bundle dry-run
checks decide whether app-interface configuration changed, not whether LDAP
membership changed. Raw snapshots include the `memberSources` configuration,
so changes to source groups/providers participate in the comparison. Existing
snapshots that reuse `fetch_desired_state()` with cached LDAP responses, such as
`github-org`, remain valid. Wet runs execute without the comparison-bundle gate.

Supported consumers are `gitlab-members`, `acs-rbac`, `openshift-groups`,
`ocm-groups-api`, `github-org`, `github-owners-api`, and `change_owners`, in
addition to `openshift-rolebindings`, `openshift-clusterrolebindings`,
`openshift-users`, `sendgrid-teammates`, `automated-actions-config`,
`glitchtip-api`, `ocm-aws-infrastructure-access`,
and `slack-usergroups-api`'s promoted role-permission pilot and cluster-access path.
Slack cluster access preserves user/role `tag_on_cluster_updates` precedence and
local tagging overrides, including for LDAP members without GitHub accounts.
All Slack membership collectors retain canonical `org_username` values. Gov Slack
names are translated once while constructing the client-side qontract-api POST
request, using the complete app-interface user list; unknown identities retain
their canonical username. This includes PagerDuty-derived users. Internal desired
state remains canonical and is not mutated during request construction.
Reporters, CLI consumers, and `vault-manager` remain separate workstreams.
OCM group reconciliation uses `ocm-groups-api`; the retired `ocm-groups`
integration is not part of this rollout or its manual test matrix.
`change_owners` accepts providers with `hasAuditTrail: false`; its role authorization
still comes from the comparison bundle. `github-owners-api` remains add-only. Consumers needing
`quay_username`, `public_gpg_key`, or `pagerduty_username` cannot use LDAP-only
members; those attributes are outside the LDAP provider's scope.

Changes to legacy `ldap-groups` are excluded from this rollout while its
qontract-api migration is handled separately:
https://github.com/app-sre/qontract-reconcile/pull/5846.
Its existing source/publish circular-dependency validation remains unchanged.

OpenShift user cleanup retains its existing scope: namespace RoleBinding and group
memberships, now including LDAP-resolved users in those paths. ClusterRoleBinding
cleanup is not added by this rollout. Service-account bots stay on their existing
binding path. `gitlab-housekeeping` retains its existing explicit-user authorization
path and is excluded from this LDAP membership migration.

The infrastructure-access consumer preserves `aws_username` overrides and
requires already-provisioned IAM users before source-backed grants.
The prerequisite read requires IAM `ListUsers` access. Missing principals abort
before grant removals; membership resolution does not provision users,
PGP keys, or credential delivery. Keep explicit identity/provisioning data for
`terraform-users`, and do not treat this check as authorization to remove it.
`aws-iam-password-reset` retains its existing behavior; its membership and
GraphQL migrations are out of scope for this rollout.

### Rollout Prerequisites

Before enabling sources for each integration:

- Allow its GraphQL queries to read membership-provider definitions and LDAP
  settings in app-interface's integration permissions.
- Supply the configured qontract-api server/token and Vault server URL to
  legacy integration and MR-check jobs as well as API integrations.
- Deploy the LDAP API response containing required member `name` before consumers
  using the regenerated client. The group-members cache uses a new versioned key
  so old entries without names are not reused. Missing LDAP person names fail
  resolution rather than producing incomplete users.
- Verify LDAP credentials and source groups; retain the source/publish conflict
  checks in `ldap-groups`.
- Run a dry-run with explicit-only, LDAP-only, and hybrid roles, review the
  membership diff, then promote and verify the integration. Record progress in
  https://redhat.atlassian.net/browse/APPSRE-15463.

Unit tests mock external systems; they do not constitute production dry-run or
promotion verification.
